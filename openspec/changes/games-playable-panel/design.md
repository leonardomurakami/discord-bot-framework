## Context

The games plugin (`plugins/games/`) already implements trivia, angle, and RPS as Discord commands backed by SQLAlchemy models (`TriviaStats`, `AngleGame`, `AngleStats`, `RPSStats`, plus achievement tables). The plugin inherits `DatabaseMixin` and `WebPanelMixin`; its web panel (`plugins/games/web/routes.py`, `plugins/games/templates/panel.html`) currently exposes a single achievements view loaded over HTMX. The plugin's `plugin.py` already contains reusable async helpers — `award_points`, `get_leaderboard`, `process_angle_guess`, `record_rps_result`, `get_or_create_angle_game`, `get_trivia_stats`, `get_angle_stats`, `get_rps_stats` — that take `(user_id, guild_id)` and are not coupled to a Discord context. The angle protractor image is generated by `plugins/games/utils/angle_image.py::generate_angle_image(target)`, which returns PNG bytes and has no Discord dependencies.

The framework's established interactive-panel pattern is HTMX: the fun plugin (`plugins/fun/`) uses `hx-post` forms that return `HTMLResponse` fragments, and the games achievements view already uses `hx-get` with `hx-trigger="load, guild-changed from:body"` and reads the selected guild from `localStorage.getItem('selectedGuildId')`. User identity comes from `DiscordAuth` (`auth.is_authenticated(request)`, `auth.get_current_user(request)`), which returns the Discord user ID. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Make trivia, angle, and RPS playable from the web panel using HTMX, reusing the existing plugin helpers and DB models so web-played and Discord-played games share stats.
- Add leaderboards and stats views to the panel.
- Add an image-generation route for the angle protractor.
- Add the first test suite for the games plugin.

**Non-Goals:**
- Multiplayer trivia on the web (web is single-player only; Discord retains multiplayer).
- New Discord commands (`/rps-stats`, `/angle-achievements`, `/rps-achievements` are out of scope).
- Custom question management UI (the permission nodes exist but the feature is unimplemented — not building it).
- GuildLeaderboard caching implementation (out of scope; leaderboards query TriviaStats directly as the existing `get_leaderboard` helper already does).
- Changing the existing achievements view's behavior (it becomes one section among several).

## Decisions

### 1. Reuse existing plugin helpers for all web game logic
The web routes call `plugin.award_points`, `plugin.process_angle_guess`, `plugin.record_rps_result`, `plugin.get_leaderboard`, and the stats getters directly. These already accept `(user_id, guild_id)` and write to the same models the Discord commands use, so web play and Discord play share stats with no duplication.

**Rationale:** The helpers were written context-agnostic; only the command/view modules depend on Hikari/Lightbulb/Miru. Reusing them keeps a single source of truth for scoring and stats.
**Alternative considered:** Duplicating logic in the web module — rejected because it would diverge from Discord-played scoring and double the maintenance.

### 2. Extract a shared trivia question-fetch helper
The trivia command currently inlines question fetching (API → custom questions → defaults) inside the command handler. To avoid duplicating this in the web route, extract a `plugin.fetch_trivia_question(guild_id, difficulty, category)` async helper that returns a normalized question dict (with shuffled choices). Both the Discord command and the web route call it.

**Rationale:** The fetch logic (API params, fallback chain, HTML unescaping) is non-trivial and must be identical across surfaces.
**Alternative considered:** Calling the existing inline code via a thin wrapper — rejected because the inline code is entangled with `ctx` and embed construction.

### 3. HTMX fragment pattern (match the fun panel)
Each interactive game is an HTMX exchange returning `HTMLResponse` fragments, mirroring `plugins/fun/web/routes.py`. Trivia: `GET /plugin/games/api/trivia/question` returns the question fragment; `POST /plugin/games/api/trivia/answer` returns the result + next-question button. Angle: `GET /plugin/games/api/angle/start` returns the game fragment (with an `<img>` pointing at the image route); `POST /plugin/games/api/angle/guess` returns the updated fragment. RPS: `POST /plugin/games/api/rps/play` returns the outcome fragment. Leaderboards and stats use `GET` endpoints returning fragments, consistent with the existing achievements endpoint.

**Rationale:** HTMX is the established panel interactivity pattern; fragments keep the panel a single page with no client-side framework.
**Alternative considered:** A JSON API + React — rejected; the framework standardizes on HTMX/server-rendered fragments.

### 4. Angle image served by a dedicated route
Add `GET /plugin/games/api/angle/image?target=<n>` that calls `generate_angle_image(target)` and returns a `Response` with `media_type="image/png"`. The angle game fragment references it via `<img src="...">`. Because the image contains no labels, the target value is safe to pass as a query param (it only controls the visual; the authoritative target lives in the DB game record / in-memory replay state, which the guess endpoint consults).

**Rationale:** `generate_angle_image` already returns PNG bytes and is Discord-agnostic; a route is the natural web analog of the Discord attachment.
**Alternative considered:** Embedding the PNG as a base64 data URI in the fragment — rejected because it bloats the HTML and prevents browser caching; a separate route lets the browser cache the image.

### 5. Section navigation via HTMX partial loads
The panel gains a section switcher (Play / Leaderboards / Stats / Achievements). Switching sections issues an `hx-get` to a section endpoint that returns the section's initial fragment, swapping into a main content area. This mirrors the admin-panel-parity approach and keeps the panel a single route (`/plugin/games`).

**Rationale:** Avoids multi-route panel sprawl and preserves the guild-selector integration (`guild-changed` event already wired in the achievements view).
**Alternative considered:** Separate FastAPI routes per section — rejected; a single page with fragment swaps matches the existing panel conventions.

### 6. Auth and guild context handling
Every game/leaderboard/stats endpoint follows the existing achievements endpoint's pattern: get `auth` via `_get_auth(plugin)`, require `auth.is_authenticated(request)`, read the Discord user ID from `auth.get_current_user(request)`, and read `guild_id` from the request (form field or query param, sourced from `localStorage.getItem('selectedGuildId')` on the client). Missing auth → login-prompt fragment; missing/invalid guild → select-a-server fragment. No endpoint mutates state without both.

**Rationale:** Consistent with the existing achievements route and the framework's `DiscordAuth` guard rails.
**Alternative considered:** FastAPI dependency injection for auth — deferred; the existing games routes use the inline pattern and consistency matters more than refactoring here.

### 7. Web trivia is single-player; stats still count
Web trivia records against the authenticated user's `TriviaStats` in the selected guild, exactly as Discord trivia does. There is no multiplayer lobby on the web. Streaks, points, and achievements accumulate across both surfaces.

**Rationale:** The DB models are per-user-per-guild, so web play naturally contributes to the same records. Multiplayer would require real-time coordination outside this change's scope.

### 8. Timer is client-side JavaScript
The trivia countdown is rendered in the fragment and driven by a small inline JS timer (as the Discord command uses a Discord timestamp). The time-attack bonus is applied server-side using the elapsed time between question fetch and answer POST (the route records a server-side start timestamp or the client sends the elapsed time, validated server-side).

**Rationale:** Keeps the timer visible without a websocket; server-side elapsed-time check prevents client tampering with the bonus.
**Alternative considered:** Pure client-side timing — rejected for the bonus because it's trivially spoofable.

### 9. Test strategy
Tests live under `tests/unit/plugins/games/` and use the existing `tests/conftest.py` fixtures (mock bot, mock DB manager, `AsyncSessionMock`, `async_context_manager`). Three test modules:
- `test_game_logic.py` — pure logic: trivia scoring (`award_points` math), `get_daily_angle` determinism, `angle_distance`/`angle_direction`, RPS outcome for all 9 combinations.
- `test_web_routes.py` — FastAPI `TestClient` against a routes-registered app with a stubbed plugin (mock auth returning a fixed user, mock helpers returning canned stats/game states); asserts fragment content, PNG content-type, auth gating, and that stats helpers are called.
- `test_stats_recording.py` — integration-style: verify `award_points`/`process_angle_guess`/`record_rps_result` persist expected fields and trigger achievement checks, using the mock DB session.

**Rationale:** Follows the repo's existing test layout (`tests/unit/plugins/<name>/`) and async fixtures; mirrors how `tests/unit/plugins/fun/test_fun_plugin.py` exercises plugin logic.
**Alternative considered:** Full end-to-end DB tests — deferred; the mock-session pattern is the repo standard and keeps tests fast.

## Risks / Trade-offs

- **[Shared stats between web and Discord could inflate leaderboards]** → Mitigation: this is intended (web play is real play); single-player web trivia awards the same points as Discord single answers, so it's not a new advantage. No separate "web" stat bucket is needed.
- **[Trivia question-fetch extraction could regress the Discord command]** → Mitigation: extract the helper as a pure refactor first, keep the command calling it, and add a test for the helper before touching the web route.
- **[Angle image route exposes the target via query param]** → Mitigation: the image has no labels and the target is only authoritative in the DB/in-memory state consulted by the guess endpoint; a user could already infer the target by playing. No sensitive data is leaked.
- **[Client-side timer spoofing for time-attack bonus]** → Mitigation: compute elapsed time server-side from a start timestamp issued with the question; ignore any client-supplied timing for the bonus.
- **[No existing tests means the first suite must also establish fixtures/mocks for the games plugin]** → Mitigation: reuse `tests/conftest.py` fixtures; add a small games-specific fixture module only if needed.
- **[matplotlib image generation is synchronous and CPU-bound]** → Mitigation: `generate_angle_image` is fast (~tens of ms) and already used synchronously in the Discord command; for the web route it runs in the async handler. If profiling shows blocking, wrap in `asyncio.to_thread` — deferred until measured.

## Migration Plan

1. Extract `fetch_trivia_question` helper from the trivia command (no behavior change; command still works).
2. Add the new HTMX endpoints and image route to `routes.py`; add section navigation and game fragments to `panel.html`.
3. Add the test modules; run `uv run pytest tests/unit/plugins/games`.
4. Rollout is a plugin reload — no DB schema changes (existing models suffice), no new dependencies.
5. Rollback: revert the routes/templates; the extracted helper and existing command behavior are unaffected.

## Open Questions

- Should web-played trivia questions be deduplicated per session (avoid repeating the same question back-to-back)? The Discord command doesn't deduplicate; matching that behavior is simplest and can be revisited later without changing the spec.
